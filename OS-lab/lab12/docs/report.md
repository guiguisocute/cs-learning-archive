# 段页式存储管理模拟实验报告

## 一、实验目的

1. 理解段页式存储管理的基本思想，掌握位示图、段表和页表三者之间的协同关系。
2. 掌握基于位示图的物理块分配与回收机制，理解"顺序扫描空闲块并标记占用"的实现方式。
3. 掌握段页式地址转换的完整流程，理解"作业名→段号→页号→页内偏移→物理地址"的逐级映射关系。
4. 通过多组边界测试（空间不足、重名作业、越界地址等），加深对分配失败处理和越界检查重要性的理解。

## 二、实验内容

编写一个段页式存储管理模拟程序。程序从终端读取主存大小、系统字长和块长，初始化位示图后进入交互式菜单循环。支持四种操作：内存分配（读取作业名、大小、段数和每段页数，顺序分配物理块）、内存回收（按作业名释放所有占用块）、地址转换（按作业名和逻辑地址查询物理地址）、查看当前内存状态（输出位示图和所有作业的段表/页表）。

结合当前代码实现，本实验实际完成了以下内容：

1. 通过 `memory_system` 结构体统一管理主存参数、位示图、物理块占用数组和作业链表。
2. 通过 `mem_configure()` 根据主存大小和块长计算总块数和位示图行数，动态分配位示图和占用数组。
3. 通过 `mem_allocate_job()` 实现作业分配，包括重名检查、空间检查、顺序扫描空闲块、构造作业结点、填写段表和页表、更新位示图。
4. 通过 `mem_recycle_job()` 实现作业回收，使用二级指针在单链表中定位并删除目标作业，遍历页表释放所有占用块。
5. 通过 `mem_translate()` 实现地址转换，按"作业→段号→页号→偏移"顺序逐级校验合法性，最终计算物理地址。
6. 通过 `io_print_bitmap()` 和 `io_print_job_detail()` 实现位示图和段表/页表的格式化输出。
7. 通过 12 组测试用例验证正常分配、刚好装满、连续多作业、回收恢复、重名拒绝、空间不足、容量不匹配、地址转换成功、段号越界、页号越界、偏移越界和连续回收等场景下的正确性。

## 三、实验过程概述

本实验分为 5 个阶段：理解与分析、数据结构设计、核心程序实现、调试与结果验证、实验总结。

各阶段任务概括如下：

1. 理解与分析阶段：明确段页式存储管理中位示图、段表、页表三者的职责与协同关系，重点理解"分配时三者必须同步更新，回收时三者必须同步恢复"的一致性要求。
2. 数据结构设计阶段：理解 `memory_system`、`job_node`、`segment_entry`、`page_entry` 四个核心数据结构的字段含义和层次关系。

5. 实验总结阶段：根据程序实现与测试结果，分析段页式管理的特点与实现要点，整理形成实验报告。

## 四、理解与分析

段页式存储管理是将分段和分页两种机制结合的内存管理方案。其基本思想是：作业的逻辑地址空间先按功能划分为若干段，每段再按固定大小划分为若干页，每页映射到一个物理块。这样既保留了段的逻辑意义（不同段可以有不同的访问权限和共享属性），又利用了页的固定大小来消除段内的外部碎片。

本实验的核心是维护三类状态的一致性：

1. **位示图**（`bitmap_words` / `block_used`）：记录每个物理块是否被占用。位示图是物理块管理的唯一依据——分配时从位示图中找空闲块，回收时在位示图中将占用块恢复为空闲。`bitmap_words` 按字长分行保存位信息（用于按行输出），`block_used` 是逐块的布尔数组（用于快速查询和扫描）。
2. **段表**（`segment_entry`）：记录每个段包含多少页。段表是段号到页表的索引——给定段号后，通过段表找到该段的页表，再从页表中查找具体的物理块号。
3. **页表**（`page_entry`）：记录每页对应的物理块号。页表是页号到物理块号的最终映射。

从当前源码可以看出，实验已经落地为以下实现思路：

1. 用 `memory_system` 结构体的 `block_used[]` 数组作为主要的空闲块判定依据，`bitmap_words[]` 同步维护用于输出展示。`set_block_state()` 函数同时更新这两个数据结构，确保一致性。
2. 用 `job_node` 单链表管理所有已装入的作业，每个作业结点包含段表数组，段表中包含页表数组，形成"作业→段→页→物理块号"的三级层次结构。
3. 分配时先统计所有段的页数之和，再一次性扫描位示图收集足够的空闲块号，最后依次分配给各段各页。这种"先收集后分配"的方式避免了分配到一半发现空间不足需要回滚的问题。
4. 回收时使用二级指针 `cursor` 遍历链表，可以在找到目标结点后直接修改前驱的 `next` 指针完成删除，无需维护额外的 `prev` 指针。

本实验的核心难点在于以下三个关键问题：

1. 三类状态的同步更新。分配时必须同时更新位示图（标记占用）、页表（记录块号）和作业链表（挂入新结点）；回收时必须同时恢复位示图（标记空闲）、从链表删除结点、释放内存。如果只更新了其中一部分，就会出现"位示图显示空闲但页表仍指向该块"或"链表中残留已回收的作业"等不一致状态。
2. 分配前的多重校验。在真正分配之前需要检查：主存是否已初始化、作业名是否重复、段数是否合法、总页数是否为正、空闲块是否足够、页表容量是否能容纳作业大小。这些校验必须全部通过后才能进入实际分配流程，否则可能产生部分更新的不一致状态。
3. 地址转换的越界检查顺序。必须按"作业→段号→页号→偏移"的顺序逐级检查，因为后一级的检查依赖前一级的结果（例如，段号合法后才能访问该段的页数来判断页号是否越界）。如果顺序错误或遗漏某一级，程序可能发生数组越界访问。

## 五、数据结构设计

本实验使用一个全局 `memory_system` 结构体管理主存状态，作业通过单链表组织，每个作业包含段表数组，段表中包含页表数组。各核心数据结构的字段如下表所示：

**主存系统结构体 `memory_system`：**

| 字段 | 类型 | 作用说明 |
| --- | --- | --- |
| `memory_size` | `int` | 主存总大小 |
| `word_length` | `int` | 系统字长，决定位示图每行的列数 |
| `block_length` | `int` | 块长（页大小），决定物理块的容量 |
| `block_count` | `int` | 物理块总数（`memory_size / block_length`） |
| `word_count` | `int` | 位示图行数（`(block_count + word_length - 1) / word_length`） |
| `free_block_count` | `int` | 当前空闲物理块数 |
| `bitmap_words` | `unsigned long long *` | 位示图数组，按字长分行保存位信息 |
| `block_used` | `unsigned char *` | 逐块占用标记数组，0=空闲，1=占用 |
| `job_list_head` | `struct job_node *` | 已装入作业的单链表头指针 |

**作业结点 `job_node`：**

| 字段 | 类型 | 作用说明 |
| --- | --- | --- |
| `name` | `char[MAX_NAME_LEN]` | 作业名称 |
| `requested_size` | `int` | 作业请求的主存大小 |
| `segment_count` | `int` | 段数 |
| `total_pages` | `int` | 所有段的总页数 |
| `segments[]` | `segment_entry[MAX_SEGMENTS]` | 段表数组 |
| `next` | `struct job_node *` | 链表后继指针 |

**段表项 `segment_entry`：**

| 字段 | 类型 | 作用说明 |
| --- | --- | --- |
| `segment_no` | `int` | 段号 |
| `page_count` | `int` | 本段的页数 |
| `pages[]` | `page_entry[MAX_PAGES_PER_SEGMENT]` | 页表数组 |

**页表项 `page_entry`：**

| 字段 | 类型 | 作用说明 |
| --- | --- | --- |
| `page_no` | `int` | 页号 |
| `block_no` | `int` | 对应的物理块号 |

这种"结构体→段表数组→页表数组"的三级嵌套设计直接映射了段页式存储管理的逻辑层次。位示图同时使用 `bitmap_words`（按位紧凑存储，用于输出）和 `block_used`（逐块布尔标记，用于快速扫描）两种表示，两者通过 `set_block_state()` 函数保持同步。

## 六、核心程序实现

本实验采用"三层分离"的结构：`main.c` 负责交互流程，`mem_model.c` 负责核心算法，`io_view.c` 负责格式化输出。

主要函数及其作用如下表所示：

| 函数名 | 所在文件 | 主要作用 |
| --- | --- | --- |
| `mem_configure()` | `mem_model.c` | 根据主存参数计算块数和位示图行数，动态分配数组 |
| `mem_init_bitmap()` | `mem_model.c` | 将位示图清零，释放已有作业链表 |
| `mem_allocate_job()` | `mem_model.c` | 作业分配：校验→收集空闲块→构造结点→更新位示图 |
| `mem_recycle_job()` | `mem_model.c` | 作业回收：链表查找→遍历页表释放块→删除结点 |
| `mem_translate()` | `mem_model.c` | 地址转换：逐级校验→查页表→计算物理地址 |
| `distribute()` | `main.c` | 读取段数和每段页数，调用分配算法并输出结果 |
| `recycle()` | `main.c` | 调用回收算法并刷新显示 |
| `io_print_bitmap()` | `io_view.c` | 按字长分行输出位示图矩阵和空闲块数 |
| `io_print_job_detail()` | `io_view.c` | 输出作业的段表和页表 |

辅助函数：

| 辅助函数 | 主要作用 |
| --- | --- |
| `set_block_state()` | 同时更新 `block_used` 和 `bitmap_words`，保持两种表示一致 |
| `count_required_pages()` | 统计所有段的页数之和 |
| `collect_free_blocks()` | 顺序扫描 `block_used`，收集指定数量的空闲块号 |
| `append_job()` | 将新作业结点追加到链表尾部 |
| `mem_find_job()` | 按作业名在链表中线性查找 |
| `free_job_list()` | 释放整个作业链表的内存 |

分配算法（`mem_allocate_job()`）的核心步骤如下：

1. 前置校验：检查主存是否初始化、作业名是否为空、段数是否合法、是否存在重名作业。
2. 统计总页数需求：调用 `count_required_pages()` 求各段页数之和。
3. 空间检查：判断总页数是否超过空闲块数，以及页表总容量是否能容纳作业大小。
4. 收集空闲块：调用 `collect_free_blocks()` 从 `block_used` 中顺序收集足够的空闲块号到临时数组中。
5. 构造作业结点：`calloc` 分配 `job_node`，填写作业名、大小、段数和总页数。
6. 填写段表和页表：依次遍历每段的每页，从临时数组取出块号写入页表，同时调用 `set_block_state()` 标记占用并递减 `free_block_count`。
7. 挂入链表：调用 `append_job()` 将作业追加到链表尾部。

回收算法（`mem_recycle_job()`）的核心步骤如下：

1. 用二级指针 `cursor` 遍历链表，找到作业名匹配的结点。
2. 将目标结点从链表中摘除（`*cursor = victim->next`）。
3. 遍历目标结点的所有段和所有页，对每个页表项中的块号调用 `set_block_state(block_no, 0)` 恢复空闲，并递增 `free_block_count`。
4. 释放目标结点的内存。

地址转换算法（`mem_translate()`）的核心步骤如下：

1. 按作业名查找作业结点，未找到则报错。
2. 检查段号是否在 `[0, segment_count)` 范围内。
3. 检查页号是否在 `[0, segments[segment_no].page_count)` 范围内。
4. 检查页内偏移是否在 `[0, block_length)` 范围内。
5. 从页表取出物理块号：`block_no = segments[segment_no].pages[page_no].block_no`。
6. 计算物理地址：`physical_address = block_no * block_length + offset`。

关键实现点汇总：

| 关键实现点 | 具体做法 | 目的 |
| --- | --- | --- |
| 双重位示图表示 | `block_used[]` + `bitmap_words[]` 通过 `set_block_state()` 同步 | 兼顾快速扫描和格式化输出 |
| 先收集后分配 | 先用临时数组收集足够空闲块，确认数量够了再开始写入 | 避免分配到一半空间不足需要回滚 |
| 二级指针删除 | 回收时用 `struct job_node **cursor` 遍历链表 | 无需 `prev` 指针即可完成单链表删除 |
| 逐级越界检查 | 地址转换按"作业→段→页→偏移"顺序检查 | 后一级依赖前一级合法才能安全访问 |
| 重名作业拒绝 | 分配前调用 `mem_find_job()` 检查是否已存在 | 防止覆盖旧作业导致内存泄漏 |

## 七、调试与结果验证

本实验在 `Ubuntu-24.04.1LTS-WSL2 x86_64 GNU/Linux` 环境下完成，使用 `gcc (Ubuntu 13.3.0-6ubuntu2~24.04.1) 13.3.0` 编译器，通过 `make student` 构建生成可执行文件 `bin/student_lab`。编译选项包含 `-std=c11 -Wall -Wextra -Werror`，确保代码无任何警告。

调试过程中主要关注以下几个问题：

1. 位示图和页表是否同步——分配后位示图中标记为 1 的块号是否与页表中记录的块号完全一致。
2. 回收后是否完全恢复——回收一个作业后，其占用的所有物理块是否都恢复为 0，空闲块数是否回到分配前的值。
3. 链表操作是否正确——连续回收多个作业后，链表是否仍然完整，不会出现悬垂指针。
4. 地址转换的越界检查是否按正确顺序执行——段号、页号、偏移三个维度的越界是否分别给出准确的错误提示。
5. 边界条件是否处理——空间刚好装满、重名作业、页表容量不匹配等极端情况是否被正确拒绝。

为验证程序正确性，使用了 12 组测试数据进行测试，结果如下表所示：

| 用例 | 主存大小 | 块长 | 主要特点 | 测试结果 |
| --- | ---: | ---: | --- | --- |
| `case_sample` | 1024 | 1 | 标准分配，job1 有 2 段共 30 页 | 分配成功，块 0-29 占用，剩余 994 |
| `case_small_fit` | 4 | 1 | 刚好装满 4 块 | 分配成功，剩余 0 |
| `case_multi_job` | 16 | 1 | 连续装入 job1、job2，回收 job1 | 回收成功，job1 的块恢复空闲，剩余 12 |
| `case_multi_recycle_chain` | 20 | 1 | 装入 job1、job2，依次回收 | 两次回收后剩余恢复到 20 |
| `case_no_space` | 4 | 1 | job1 占 3 块后 job2 需要 2 块 | job2 报"主存空间不足" |
| `case_duplicate_job` | 16 | 1 | 重复装入同名 job1 | 第二次报"已存在，不能重复装入" |
| `case_page_capacity_mismatch` | 8 | 2 | 作业大小 5 但只有 2 页×2 块长=4 | 报"页表容量不足" |
| `case_address_ok` | 16 | 1 | 合法地址转换 (段1,页1,偏移0) | 物理块 3，物理地址 3 |
| `case_address_oob` | 16 | 1 | 页号越界 (段0,页5,偏移0) | 报"页号越界" |
| `case_address_segment_oob` | 16 | 1 | 段号越界 (段2) | 报"段号越界" |
| `case_address_offset_oob` | 16 | 1 | 偏移越界 (偏移1，块长1) | 报"页内偏移越界" |
| `case_recycle_missing` | 16 | 1 | 回收不存在的作业 ghost | 报"未找到作业 ghost" |

从测试结果可以看出：

1. 在标准分配场景（`case_sample`）中，主存 1024 块、块长 1，job1 有 2 段分别需要 10 页和 20 页，共 30 页。分配后物理块 0-29 被标记为占用，剩余空闲块数从 1024 变为 994，位示图中前 30 位为 1，其余为 0，段表和页表中的块号与位示图完全一致。
2. 在刚好装满场景（`case_small_fit`）中，主存只有 4 块，作业 tiny 需要 4 页，分配后剩余空闲块数为 0。这验证了"空闲块数恰好等于需求"时仍能正确分配的边界处理。
3. 在连续回收场景（`case_multi_recycle_chain`）中，先装入 job1（4 页）和 job2（6 页），共占 10 块；依次回收后空闲块数恢复到 20，位示图全部清零。这证明了每次回收都完整遍历了页表并恢复了所有块。
4. 在地址转换场景（`case_address_ok`）中，job1 有 2 段各 2 页，块长 1。查询 (段1, 页1, 偏移0) 对应物理块 3（段0 占块 0-1，段1 占块 2-3，页1 对应块 3），物理地址 = 3 × 1 + 0 = 3。结果正确。
5. 三组越界场景分别验证了段号、页号和偏移的越界检查：`case_address_segment_oob` 中段号 2 超过段数 2（有效范围 0-1），`case_address_oob` 中页号 5 超过页数 4（有效范围 0-3），`case_address_offset_oob` 中偏移 1 超过块长 1（有效范围仅 0）。三种越界均被正确识别并给出对应错误提示。
6. 重名拒绝（`case_duplicate_job`）和回收不存在（`case_recycle_missing`）两个场景分别验证了分配和回收的前置校验逻辑，确保非法操作不会破坏系统状态。

## 八、实验总结

通过本次实验，我对段页式存储管理有了更具体的理解。与教材中的概念描述相比，自己实现并调试后更容易把握以下几个关键点：

1. 位示图、段表和页表的一致性是整个实验的核心约束。任何一次分配或回收操作，都必须同时更新这三类状态。最初调试时曾出现"页表正确但位示图未更新"的问题——分配时只把块号写入了页表，忘了调用 `set_block_state()` 标记占用，导致位示图仍显示全部空闲，下一次分配会重复分配相同的块。通过在循环中为每个页表项同步调用 `set_block_state()` 解决了这个问题。
2. 先收集后分配的策略避免了回滚复杂性。如果边扫描边分配，当发现中途空间不足时需要把已分配的块全部回滚。本实验采用的方式是先用临时数组收集足够的空闲块号，确认数量足够后才开始写入页表和更新位示图，从而将"是否够"和"实际分配"两个步骤分离，简化了错误处理。
3. 二级指针删除链表结点的技巧很实用。传统的单链表删除需要维护 `prev` 指针，而使用 `struct job_node **cursor = &head` 的方式可以直接通过 `*cursor = victim->next` 完成删除，不需要区分头结点和中间结点的特殊情况。在 `case_multi_recycle_chain` 中连续回收两个作业的测试证明了这种方式的正确性。
4. 地址转换的越界检查必须严格按层次顺序执行。段号越界时不能访问段表（否则数组越界），页号越界时不能访问页表，偏移越界时不能计算物理地址。三组越界测试分别验证了每一级检查的独立性和准确性。
5. 物理地址的计算公式 `块号 × 块长 + 页内偏移` 虽然简单，但前提是所有前置检查已通过。在 `case_address_ok` 中，块长为 1 且偏移为 0，物理地址直接等于块号（3），这个特殊情况反而容易让人忽略公式中块长的乘法因子。

从实现角度看，本实验练习了动态内存管理（`calloc`/`free`）、单链表操作（二级指针遍历与删除）、位运算（位示图的位级操作）、多级索引结构（作业→段→页→块）和多重前置校验等基础编程方法。12 组测试用例的运行结果表明，当前程序已经能够正确处理标准分配、边界装满、连续多作业、回收恢复、重名拒绝、空间不足、容量不匹配、地址转换和各类越界等场景。

在实际操作系统中，段页式管理是 x86 架构早期的核心内存管理方案（如 Intel 80386），现代操作系统（如 Linux）虽然在硬件层面仍支持分段，但实际上将所有段的基址设为 0、界限设为最大，实质上退化为纯分页管理。本实验通过模拟完整的段页式流程，有助于理解这一历史演进背后的设计权衡。
