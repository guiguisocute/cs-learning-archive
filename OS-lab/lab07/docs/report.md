# 固定分区存储管理实验报告

## 一、实验目的

1. 理解固定分区存储管理的基本思想，掌握分区表的组织方式和状态记录方法。
2. 掌握首次适应分配算法的实现原理，理解"容量足够且空闲"的双重判定条件。
3. 熟悉使用 C 语言实现分区分配与回收的方法，包括数组遍历查找、字符串比较、作业名规范化和状态字段管理。
4. 通过多组样例运行和结果分析，观察内碎片现象和分区利用情况，加深对固定分区方式优缺点的理解。

## 二、实验内容

编写一个固定分区存储管理模拟程序。程序从终端读取分区数和各分区信息（编号、大小、起址），再读取若干作业的大小，按首次适应策略将作业分配到分区中。分配完成后进入回收循环，用户输入作业名（支持数字和 JOB 前缀两种格式），程序找到对应分区并释放。每次分配或回收后输出当前分区表状态。

结合当前代码实现，本实验实际完成了以下内容：

1. 设计 `partition_info` 结构体，包含分区号、大小、起址和状态四个字段。
2. 通过 `input()` 完成分区信息的交互式输入，初始化状态为空字符串（表示空闲）。
3. 通过 `allocate_job_to_partition()` 实现首次适应分配：按分区表顺序查找第一个容量足够且空闲的分区，将作业名写入其状态字段。
4. 通过 `recycle_job_by_name()` 实现作业回收：支持 `"2"` 和 `"JOB2"` 两种输入格式，通过 `normalize_job_name()` 统一规范化后按名称查找并释放分区。
5. 通过 `print()` 输出分区表，空闲显示 `0`，已占用显示作业名。
6. 通过 6 组测试用例验证常规分配回收、无合适分区、精确匹配、单分区、JOB 前缀输入和回收后再分配等场景下的正确性。

## 三、实验过程概述

本实验分为 5 个阶段：理解与分析、数据结构设计、核心程序实现、调试与结果验证、实验总结。

各阶段任务概括如下：

1. 理解与分析阶段：明确固定分区分配的输入输出，重点理解分区状态管理和首次适应策略，分析分配条件为什么是"容量足够且空闲"而非其中一个。
2. 数据结构设计阶段：理解 `partition_info` 结构体各字段的含义，确定用空字符串表示空闲、作业名字符串表示已占用的状态编码方式，并确定分配和回收的模块划分。
3. 核心程序实现阶段：完成 `allocate_job_to_partition()` 和 `recycle_job_by_name()` 两个核心函数的实现。
4. 调试与结果验证阶段：使用仓库中的样例数据和新增边界用例运行程序，检查分配结果、回收操作和分区状态更新是否正确。
5. 实验总结阶段：分析内碎片现象和固定分区的局限性，整理形成实验报告。

## 四、理解与分析

固定分区存储管理是最简单的多道程序存储管理方式。系统在初始化时将用户内存区划分为若干固定大小的分区，每个分区在运行期间大小不变。当作业申请内存时，系统查找一个"容量足够且当前空闲"的分区分配给它；作业完成后释放该分区，使其重新可用。与可变分区不同，固定分区的分区边界在系统启动后不再改变，因此不存在分区合并或分裂的问题。

本实验采用的决策规则是：

1. 分区表按编号顺序组织，每个分区记录编号、大小（KB）、起址（KB）和当前状态。分区表使用 1-indexed 数组，便于与用户交互中的分区编号对应。
2. 状态字段为空字符串表示空闲，包含作业名（如 `JOB1`）表示已占用。输出时空闲分区显示 `0`，已占用分区显示作业名。
3. 分配时按分区表顺序扫描，找到第一个满足 `size_kb >= job_size` 且状态为空闲的分区，将作业名写入状态字段。这就是首次适应（First Fit）策略。
4. 回收时根据作业名查找对应分区，将状态字段清空（恢复为空字符串）。回收后分区大小和起址不变，仅状态改变。
5. 输入作业名时兼容数字格式（`"2"`）和完整格式（`"JOB2"`），通过 `normalize_job_name()` 统一处理。该函数检查输入是否以 `"JOB"` 开头，若不是则自动添加前缀。

从当前源码可以看出，实验已经落地为以下实现思路：

1. 用全局数组 `partitions[]` 保存分区表，用全局数组 `job_sizes[]` 保存作业大小。
2. 分配在 `main()` 中通过 `for` 循环依次调用 `allocate_job_to_partition()`，每个作业按编号自动构造作业名。
3. 回收在 `main()` 中通过 `while(1)` 循环交互式执行，每次读取用户输入的作业名并调用 `recycle_job_by_name()`。
4. 通过 `is_partition_free()` 辅助函数封装空闲判断逻辑，使分配函数的代码更清晰。

本实验的核心难点在于以下几个关键问题：

1. 分配条件是双重判定。仅容量足够不够，还必须是空闲分区——已被占用的 128KB 分区不能再分配给新作业，即使它的容量远超作业需求。仅空闲也不够，还必须容量足够——空闲的 12KB 分区无法装入 30KB 的作业。在 `case1.in` 中，JOB1（30KB）跳过分区 1（12KB，容量不足）直接进入分区 2（32KB），体现了这一双重判定。
2. 内碎片不可避免。30KB 的作业进入 32KB 的分区后，分区内剩余 2KB 空间无法再被利用，形成内碎片。在 `case1.in` 中，JOB3（90KB）进入分区 4（128KB），浪费了 38KB，内碎片率高达 29.7%。这是固定分区方式的固有缺陷。
3. 作业可能无法分配。如果所有分区都已被占用，或所有空闲分区的容量都小于作业大小，作业将无法装入。在 `case_no_fit.in` 中，JOB2（50KB）在最大分区仅 30KB 的系统中无法分配。
4. 首次适应策略的局限性。首次适应总是选择第一个容量足够的空闲分区，这可能导致小作业占据大分区，使后续大作业无分区可用。例如如果 30KB 作业先占了 128KB 分区，后来的 120KB 作业就只能进入更大的分区或无法分配。

## 五、数据结构设计

为便于实现固定分区存储管理程序，本实验使用 `partition_info` 结构体表示每个分区的信息。各字段的作用如下表所示：

| 字段 | 类型 | 作用说明 |
| --- | --- | --- |
| `id` | `int` | 分区编号，用于输出显示和用户交互 |
| `size_kb` | `int` | 分区大小（KB），初始化后不再改变 |
| `start_kb` | `int` | 分区起始地址（KB），初始化后不再改变 |
| `status` | `char[JOB_NAME_LEN]` | 分区状态：空字符串表示空闲，作业名表示已占用 |

此外还使用以下全局数据：

| 变量 | 类型 | 作用说明 |
| --- | --- | --- |
| `n` | `int` | 分区数，决定分区表的有效长度 |
| `m` | `int` | 作业数，决定分配循环的次数 |
| `job_sizes[]` | `int[MAX_JOBS+5]` | 各作业的大小（KB），1-indexed |
| `partitions[]` | `partition_info[MAX_PARTITIONS]` | 分区表，1-indexed |

使用空字符串而非字符 `"0"` 表示空闲状态，有两个好处：一是可以用 `status[0] == '\0'` 快速判断分区是否空闲，无需调用 `strcmp()`；二是避免了与可能的作业名 `"0"` 混淆。输出时空闲分区显示 `0`，这个 `0` 是在 `print()` 函数中根据 `is_partition_free()` 的返回值硬编码输出的，与 `status` 字段的内部表示无关。

与后续的可变分区实验相比，固定分区不需要维护空闲链表或进行分区合并，数据结构更加简单。每个分区的 `size_kb` 和 `start_kb` 在初始化后不再改变，只有 `status` 字段在分配和回收时切换。

## 六、核心程序实现

本实验采用"主函数控制交互流程，功能函数分模块实现"的结构。整体流程是：先读取分区信息并输出初始状态，再读取作业大小并依次分配，最后进入回收循环直到用户退出。

主要函数及其作用如下表所示：

| 函数名 | 主要作用 | 所处阶段 |
| --- | --- | --- |
| `input()` | 读取单个分区的编号、大小和起址，初始化状态为空闲 | 输入阶段 |
| `print()` | 输出当前分区表，空闲显示 `0`，已占用显示作业名 | 输出阶段 |
| `allocate_job_to_partition()` | 首次适应分配：查找第一个容量足够且空闲的分区 | 分配阶段 |
| `recycle_job_by_name()` | 按作业名查找并释放分区，恢复为空闲状态 | 回收阶段 |

辅助函数：

| 辅助函数 | 主要作用 |
| --- | --- |
| `is_partition_free()` | 判断分区是否空闲（`status[0] == '\0'`） |
| `normalize_job_name()` | 将 `"2"` 规范化为 `"JOB2"`，保持 `"JOB2"` 不变 |

分配算法的步骤：

1. 根据作业索引 `job_index` 用 `snprintf()` 构造作业名 `"JOB{index}"`（例如 `"JOB1"`、`"JOB2"`）。
2. 从分区 1 开始顺序扫描分区表，直到分区 n。
3. 对每个分区检查双重条件：`partitions[i].size_kb >= job_sizes[job_index]`（容量足够）且 `is_partition_free(&partitions[i])`（当前空闲）。
4. 找到第一个满足条件的分区后，用 `snprintf()` 将作业名写入 `status` 字段，立即返回 `true`。
5. 如果扫描完所有分区仍未找到合适的，返回 `false`。

回收算法的步骤：

1. 调用 `normalize_job_name()` 将用户输入统一为 `"JOB{number}"` 格式。该函数通过 `strncmp(raw_name, "JOB", 3)` 判断输入是否已包含前缀。
2. 遍历分区表，用 `strcmp()` 比较每个分区的 `status` 与规范化后的作业名。
3. 找到匹配的分区后，将 `status[0]` 置为 `'\0'`（恢复为空字符串），返回 `true`。

为了让实现更清晰，程序对关键设计点进行了拆分：

| 关键实现点 | 具体做法 | 目的 |
| --- | --- | --- |
| 状态编码 | 空字符串 = 空闲，作业名 = 已占用 | 避免额外的布尔标记，减少状态不一致的风险 |
| 首次适应 | 找到第一个满足条件的分区后立即 `return true` | 保证选择地址最低的合适分区 |
| 作业名规范化 | `normalize_job_name()` 兼容数字和 JOB 前缀输入 | 提升用户交互的灵活性 |
| 输出格式 | 空闲时输出 `0`，占用时输出作业名 | 与教材和老师截图保持一致 |

## 七、调试与结果验证

本实验在 `Ubuntu-24.04.1LTS-WSL2 x86_64 GNU/Linux` 环境下完成，使用 `gcc (Ubuntu 13.3.0-6ubuntu2~24.04.1) 13.3.0` 编译器，通过 `make` 构建生成可执行文件 `build/fixed_partition_lab`。

调试过程中主要关注以下几个问题：

1. 分配时是否同时检查了容量和空闲两个条件，遗漏任一条件都会导致错误分配。
2. 首次适应是否在找到第一个合适分区后立即停止扫描，而非继续扫描后面的分区。
3. 回收时 `normalize_job_name()` 是否能正确处理数字（`"2"`）和 JOB 前缀（`"JOB2"`）两种输入格式。特别注意 `"JOB"` 前缀的检测使用 `strncmp()` 而非 `strcmp()`，只比较前 3 个字符。
4. 回收后分区状态是否正确恢复为空闲（空字符串），后续分配能否重新使用该分区。
5. 作业名是否正确生成。`snprintf(job_name, sizeof(job_name), "JOB%d", job_index)` 对于 `job_index = 1` 生成 `"JOB1"` 而非 `"JOB01"`，确保与回收时的名称匹配。
6. 分区表的 1-indexed 下标是否在所有循环中正确使用（从 `i = 1` 到 `i <= n`）。

为验证程序正确性，使用了 6 组测试数据进行测试，结果如下表所示：

| 用例 | 主要特点 | 分区数 | 作业数 | 测试结果 |
| --- | --- | ---: | ---: | --- |
| `case1.in` | 经典分配回收流程 | 5 | 3 | JOB1→分区2，JOB2→分区3，JOB3→分区4，逐一回收恢复 |
| `case_no_fit.in` | 作业大于所有空闲分区 | 3 | 2 | JOB1(25KB)→分区3(30KB)，JOB2(50KB)无分区可用 |
| `case_exact_fit.in` | 作业大小恰好等于分区大小 | 3 | 3 | 三个作业精确填满三个分区，零内碎片 |
| `case_single_partition.in` | 单分区系统 | 1 | 1 | 分配后回收，分区恢复空闲 |
| `case_jobname_format.in` | 使用 JOB 前缀格式回收 | 3 | 2 | 输入 `JOB1`、`JOB2` 均能正确回收 |
| `case_recycle_realloc.in` | 回收后分区可重新分配 | 3 | 2 | 回收 JOB1 和 JOB2 后分区恢复空闲 |

从测试结果可以看出：

1. 在经典场景下（`case1.in`），系统有 5 个分区（12KB、32KB、64KB、128KB、100KB）。JOB1（30KB）跳过分区 1（12KB，容量不足）进入分区 2（32KB），内碎片 2KB。JOB2（60KB）跳过已占用的分区 2 进入分区 3（64KB），内碎片 4KB。JOB3（90KB）跳过已占用的分区 2、3 进入分区 4（128KB），内碎片 38KB。三次回收后所有分区恢复为空闲，分区表回到初始状态。
2. 在无合适分区场景下（`case_no_fit.in`），JOB1（25KB）进入分区 3（30KB，唯一容量足够的分区），JOB2（50KB）在扫描完分区 1（10KB）、分区 2（20KB）、分区 3（30KB，已被 JOB1 占用）后无分区可用，`allocate_job_to_partition()` 返回 `false`。这验证了当所有空闲分区都太小时程序的正确行为。
3. 在精确匹配场景下（`case_exact_fit.in`），三个作业（32KB、64KB、128KB）恰好等于三个分区的大小，内碎片为零。这在实际系统中很少出现，但验证了"大小相等时也应分配"的边界条件。
4. 在单分区场景下（`case_single_partition.in`），系统只有 1 个分区（64KB），JOB1（50KB）分配后回收，分区恢复空闲。这是最简单的边界情况。
5. 在 JOB 前缀输入场景下（`case_jobname_format.in`），用户输入 `JOB1` 和 `JOB2` 进行回收。`normalize_job_name()` 检测到输入已以 `"JOB"` 开头，直接使用而不重复添加前缀。这与输入数字 `"1"` 时自动添加前缀形成对照，验证了两种输入路径的正确性。
6. 在回收后再分配场景下（`case_recycle_realloc.in`），JOB1 和 JOB2 分配后依次回收，分区恢复空闲。回收后的分区可以被后续的新作业重新使用，验证了回收操作确实将分区状态恢复为可用。

以 `case1.in` 为例，分区 1（12KB）始终未被使用，因为所有作业的大小都超过 12KB。这反映了固定分区方式中"小分区可能永远无法被利用"的问题。而分区 5（100KB）也未被使用，尽管它足以容纳 JOB1（30KB）和 JOB2（60KB），因为首次适应策略优先选择了编号更靠前的分区 2 和分区 3。

## 八、实验总结

通过本次实验，我对固定分区存储管理有了更具体的理解。与只阅读教材中的概念描述相比，自己实现并调试后更容易把握以下几个关键点：

1. 固定分区的核心优势是实现简单、分配回收速度快。分配只需一次线性扫描，回收只需一次名称查找和一次字符串清零，不需要复杂的空闲区合并或分裂操作。整个程序的核心逻辑不到 30 行代码。
2. 固定分区的主要缺陷是内碎片不可避免。在 `case1.in` 中，JOB1（30KB）占用 32KB 分区浪费 2KB（6.3%），JOB2（60KB）占用 64KB 分区浪费 4KB（6.3%），JOB3（90KB）占用 128KB 分区浪费 38KB（29.7%）。总计浪费 44KB，占总分配空间 224KB 的 19.6%。
3. 首次适应策略简单直接，但可能不是最优选择。在本实验中，如果改用最佳适应策略（选容量最小但足够的分区），JOB1 仍进入 32KB 分区，但 JOB2 可能进入 64KB 分区、JOB3 进入 100KB 分区（浪费 10KB 而非 38KB），总浪费更少。当然，固定分区通常不讨论最佳/最坏适应——这些策略更适合可变分区场景。
4. 作业名规范化是一个实用的设计：允许用户灵活输入数字或完整名称，由程序统一处理，提升了交互体验。`normalize_job_name()` 的实现也体现了"输入宽容、内部严格"的设计原则。
5. 固定分区无法适应作业大小的变化。如果最大分区为 128KB，那么任何超过 128KB 的作业都无法运行，即使系统总空闲内存远超 128KB。这是固定分区最根本的限制，也是可变分区方式出现的动机。

从实现角度看，本实验不仅练习了首次适应分配算法本身，也练习了数组遍历查找、字符串比较与格式化（`strcmp`、`strncmp`、`snprintf`）、状态标记管理和交互式循环控制等基础编程方法。仓库中 6 组样例的运行结果表明，当前程序已经能够正确处理常规分配回收、无合适分区、精确匹配、单分区、JOB 前缀输入和回收恢复等场景。

如果继续扩展本实验，可以在同一分区表上实现最佳适应和最坏适应策略进行对比，或改为可变分区管理以消除内碎片问题。后续的 lab08 实验正是在此基础上引入了可变分区和分区合并机制。
